# Assignment 7 Faulty Module Kernel Oops Analysis

## Trigger

The kernel oops was generated by writing to the faulty device with:

`echo "hello_world" > /dev/faulty`

After executing this command, the SSH connection to the QEMU target closed and the kernel oops was displayed on the QEMU console.

## Relevant Kernel Oops Output

```text
pc : faulty_write+0x18/0x20 [faulty]
lr : vfs_write+0xf8/0x2a0

Call trace:
 faulty_write+0x18/0x20 [faulty]
 ksys_write+0x74/0x110
 __arm64_sys_write+0x24/0x30
 invoke_syscall+0x5c/0x130
 el0_svc_common.constprop.0+0x4c/0x100
 do_el0_svc+0x4c/0xc0
 el0_svc+0x28/0x80
 el0t_64_sync_handler+0xa4/0x130
 el0t_64_sync+0x1a0/0x1a4

Code: d2800001 d2800000 d503233f d50323bf (b900003f)
```

## Analysis

The program counter identifies the location of the fault as:

`faulty_write+0x18/0x20 [faulty]`

This indicates that the processor faulted 0x18 bytes from the beginning of the `faulty_write()` function in the `faulty` kernel module.

The call trace shows that the fault occurred while servicing a userspace `write()` system call. The write traveled through the kernel write path and eventually reached `faulty_write()`:

`__arm64_sys_write -> ksys_write -> faulty_write`

The `faulty_write()` function in `misc-modules/faulty.c` intentionally contains:

```c
*(int *)0 = 0;
```

This statement casts address zero to an integer pointer and attempts to write through it. Address zero represents a NULL pointer and is not a valid memory location for this operation. The attempted write therefore causes a NULL-pointer dereference and generates the kernel oops.

## Locating the Faulty Source Line

The oops reports:

`faulty_write+0x18/0x20 [faulty]`

The value `0x18` is the offset of the faulting instruction from the beginning of `faulty_write()`. The value `0x20` represents the size of the function reported by the kernel.

The module can be disassembled using the ARM64 cross-development tools to determine which instruction corresponds to this offset. For example:

`aarch64-poky-linux-objdump -dS faulty.ko`

The `faulty_write` symbol can then be located in the disassembly and the instruction at offset `0x18` examined.

The corresponding source statement in `misc-modules/faulty.c` is:

```c
*(int *)0 = 0;
```

Therefore, the kernel oops was intentionally caused by the NULL-pointer dereference inside `faulty_write()`.
